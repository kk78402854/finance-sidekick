复核中发现并修复：

1. **审计 request_id 断链**：客户端不传 `X-Request-Id` 时，响应头有自动生成的 ID，但审计表里存的是空字符串。已改为由中间件显式传入解析后的 ID，并补单测。
2. **限流器内存增长 + 清理顺序缺陷**：过期 key 永不清理；且清理若发生在取队列之后，会把当前 key 删成孤立队列导致限流失效。已增加周期性清理，并补两条回归单测。
3. **404/405 响应体不统一**：原先返回 `{"detail":"Not Found"}`。已统一为 `{"code":"NOT_FOUND",...}`，同时保留 401 等异常的原有语义与 `WWW-Authenticate` 头。
4. **业务响应体 `request_id` 为空**：`get_request_context` 只读请求头，客户端不传时响应头有 ID、响应体却是 `null`。已改为优先取中间件解析后的 ID，并补单测。
5. **文档可执行性**：PowerShell 5 不支持 `-SkipHttpErrorCheck`，已改成 `curl.exe`；单测数量与 `-q` 双静默的预期输出已按实际更正。

另外顺手加固：`request_id` 的 contextvar 重置放入嵌套 `finally`，避免日志/审计异常时上下文串号；限流键不再保存明文 token，改为 SHA-256 摘要。

## 2. 关键行为说明（测试前先理解）

### 2.1 一次请求的中间件顺序

```
RequestContext（最外层：生成 request_id、访问日志、写审计）
  └─ RateLimit（写接口限流，超限 429）
       └─ Metrics（统计 method/路由模板/状态码/耗时）
            └─ 路由 / 异常处理器
```

所以：**即使是 429 响应，也会带 `X-Request-Id`**。

### 2.2 异常语义

| 场景 | HTTP | 响应 code |
| --- | --- | --- |
| 业务异常 `AppError` | 4xx | 业务错误码（如 `CUSTOMER_NOT_FOUND`） |
| Pydantic 参数校验失败 | 422 | `VALIDATION_ERROR`，附 `details[].loc/msg/type` |
| 业务校验 `ValueError` | 400 | `BAD_REQUEST` |
| MySQL 连接不可用 | 503 | `DEPENDENCY_UNAVAILABLE` |
| 未捕获异常 | 500 | `INTERNAL_ERROR` |

### 2.3 审计范围

- 只记录 `/api/v1` 下的 `POST/PUT/PATCH/DELETE`；
- 失败不影响业务响应（写库异常只记日志）；
- `principal_hash` 不可逆，禁止明文 token 落库。

## 5. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `uv run` 卡住下载 | 无网或索引不可达 | 加 `--offline`，使用本地缓存 |
| `ModuleNotFoundError: app` | 不在项目根目录执行 | `cd` 到 `finance-data` 根目录 |
| 端口被占用 | 8099 已被使用 | 换 8098/8097 |
| 单测卡住 | 误跑了集成测试 | 只跑 `tests/unit` |
| MySQL 连不上 | 中台 `.env` 配置或服务未启动 | 检查 `.env` 的 DB 配置与 3306 端口 |
| PowerShell 报表达式错误 | `-c` 里含未转义的括号 | 用文中给出的参数化 SQL 写法，或写成临时 `.py` 文件执行 |
