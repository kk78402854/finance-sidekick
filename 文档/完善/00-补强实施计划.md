# 金融小二 · 代码补强实施计划

> 目标：按模块消灭“面试官一眼能看出的漏洞”，把工程可信度从“能跑的课程项目”提升到“可讲解、可验证、可回归的生产雏形”。
>
> 本文是执行步骤文档：先定模块与验收标准，再逐模块实施、逐模块验证，任何一步不通过不进入下一步。

## 0. 补强前的现状结论（评审基线）

| 维度 | 补强前 | 说明 |
| --- | --- | --- |
| 架构设计 | 较好 | 中台 / 客服引擎 / 门户三层清晰，流程配置化，Action 可扩展 |
| 接口与业务 | 较好 | 100 个 `/api/v1` 接口、统一响应体、字符串错误码、`request_no` 幂等 |
| 输入校验 | 弱 | 客服侧 `sender_id` 可为空、文本无长度上限；中台缺少统一兜底 |
| 异常处理 | 弱 | 客服无全局异常处理器，LLM / 网络异常可能直接 500；中台无 `Exception` 兜底与错误日志 |
| 可观测性 | 几乎为零 | 无请求 ID 串联、无结构化日志、无指标、无审计 |
| 测试 | 弱 | 只有依赖 MySQL 的集成测试，核心纯逻辑（校验器、跳转、槽位、幂等）没有单测 |
| 并发正确性 | 弱 | `dialogue_states` 整段 JSON 读改写，无版本号，存在丢更新 |
| RAG | 名义存在 | 仅转发外部 URL，本地无索引、无评测 |
| 流式输出 | 无 | 只能一次性返回整段回答 |
| CI | 无 | 没有 lint / test 门禁，README 无 badge |

对应 P0/P1/P2：M0~M3 为 P0，M4~M5 为 P1，M6 为 P2。

## 1. 模块划分与执行顺序

| 模块 | 名称 | 对应优先级 | 核心产物 |
| --- | --- | --- | --- |
| M0 | 基线治理 | P0 | ruff 配置、CI workflow、依赖分组、README badge |

4. 记录“已验证 / 遗留问题”，再进入下一模块。

## 3. M1 中台健壮性（P0）

### 现状问题
- `AppError` / `RequestValidationError` / `ValueError` 有处理器，但**没有 `Exception` 兜底**，未捕获异常直接抛给 uvicorn；
- 没有统一请求 ID：只有当调用方主动传 `X-Request-Id` 时才回传，否则 `request_id=null`；
- 日志是 print/默认 logging，无法按请求串联；
- 无指标、无限流、无审计。

### 改动清单
1. `app/logging_config.py`（新增）
   - `contextvars` 保存 `request_id`；
   - `JsonFormatter` 输出 `ts/level/logger/request_id/message/extra`；
   - `configure_logging(level)` 幂等初始化。
2. `app/middleware.py`（新增）
   - `RequestContextMiddleware`：读取/校验 `X-Request-Id`（长度 ≤ 64、仅 `[A-Za-z0-9_.-]`，非法则重新生成），写入 contextvar、响应头、访问日志（method/path/status/耗时）；
   - `RateLimitMiddleware`：滑动窗口，按“主体（Bearer token 摘要）或客户端 IP”限流，仅限制写方法，超限返回 429 `RATE_LIMITED`；
   - `AuditMiddleware`：对 `/api/v1` 写操作记录审计（见 M6）；
   - `MetricsMiddleware`：记录 method / 路由模板 / status / 耗时，写入进程内指标注册表。
3. `app/metrics.py`（新增）
   - 轻量 Counter / Histogram，输出 Prometheus 文本格式；
   - `render_metrics()` 供 `/metrics` 使用；路由模板取自 `request.scope["route"].path`，避免路径爆炸。
4. `app/audit.py`（新增）
   - `operation_audit_log` 表（`request_id / method / path / status_code / channel_code / operator_no / principal_hash / duration_ms / created_at`）；
   - 写入失败只记日志，不影响主流程；
   - token 只存 SHA-256 前 16 位，禁止落明文。
5. `app/main.py`
   - 启动时 `configure_logging()`，注册三个中间件（最外层请求 ID/访问日志/审计，其次限流，最后指标）；
   - 新增 `@app.exception_handler(Exception)`：记录堆栈，返回 500 `INTERNAL_ERROR`；
   - 新增 `@app.exception_handler(pymysql.err.OperationalError)`：返回 503 `DEPENDENCY_UNAVAILABLE`；
   - `RequestValidationError` 响应改为结构化字段列表（`loc` + `msg`），不再 `str(exc)` 全量泄漏；
   - `/health` 返回 request_id；新增 `/metrics`（默认开启，可用 `METRICS_ENABLED=0` 关闭；生产环境应通过网关或安全组限制为内网访问）；
   - lifespan 内 `ensure_audit_table()`。
6. 参数校验补齐
   - `app/utils.py`：`offset_limit` 已做上下界（`page_no` ≤ 10000、`page_size` ≤ 100），防超大 OFFSET；
   - 新增 `app/validators.py`：`ensure_non_blank`、`ensure_length`、`ensure_enum`、`ensure_date_range`，在路由入口对自由文本、枚举、时间区间做校验；
   - 对 `request_no` 统一做长度（1~64）与非空校验。

### 验收标准
- 任意请求响应头都有 `X-Request-Id`，响应体 `request_id` 与之相同；
- 人为构造未捕获异常（测试中直接调用处理器）返回 500 且日志含 request_id；
- 连续写请求超过阈值返回 429；
- `/metrics` 出现 `http_requests_total` 与 `http_request_duration_ms`；
- 新增单测全绿。

### 回滚点
中间件按“可摘除”设计：`app/main.py` 中三行 `add_middleware` 注释即恢复原行为。

## 4. M2 客服健壮性（P0）

### 现状问题
- `ChatRequest.sender_id` 无约束；`text` 无长度上限；`text` 与 `object` 同时为空会走到 `MessageType.OBJECT` 分支并被澄清，但入口没有明确报错；
- 没有全局异常处理：LLM 超时、DB 断开、未捕获异常会返回 uvicorn 默认 500 纯文本；
- 日志无法串联，调用中台也没有把 `X-Request-Id` 传下去；
- `main.py` 存在拼写错误 `mian()`。

### 改动清单
1. `assistant/conf/logging.py`（新增）：与中台一致的结构化日志 + `request_id` contextvar。
2. `assistant/api/middleware.py`（新增）：请求 ID、访问日志、简单限流（按 `sender_id`/IP）。
3. `assistant/api/schemas.py`
   - `sender_id`：`min_length=1, max_length=128`；
   - `text`：`max_length=2000`，自动 `strip`；
   - `ChatObject.type/id` 非空、`type` 限白名单（account/card/credit_card/transaction/loan/order/product）；
   - `model_validator`：`text` 与 `object` 至少一个存在；
   - `attributes` 默认工厂改为 `Field(default_factory=dict)`，避免可变默认值。
4. `assistant/api/app.py`
   - 注册中间件；`RequestValidationError` → 422 统一 JSON；`Exception` → 500 `INTERNAL_ERROR`；
   - `/health` 返回服务状态、RAG 索引状态。
5. `assistant/api/chat_router.py`
   - 从请求上下文取 `request_id`，透传到 service，再透传到 `finance_headers`（M1 已支持）；
   - `HistoryResponse` 对空历史返回空列表而不是异常（已满足，补测试）。
6. `assistant/utils/finance_client.py`
   - `finance_request` 支持 `request_id` 参数（向后兼容默认 None）；
   - 增加超时分类：`httpx.TimeoutException` → “响应超时”，`ConnectError` → “网络不可达”。
7. `assistant/main.py`：修正 `mian` → `main`，保留兼容别名。

### 验收标准
- 空 `sender_id`、空文本且无对象、超长文本均返回 422 且字段明确；
- 未捕获异常返回 500 且带 request_id；
- 客服响应的 `X-Request-Id` 与日志一致；
- 新增单测全绿。

## 5. M3 并发一致性（P1）

### 现状问题
`dialogue_states` 以 `sender_id` 为主键、`state_json` 整段覆盖，读改写之间没有版本控制。两个并发请求都基于 v1 修改，后写覆盖先写，表现为“用户刚补的槽位/任务丢了”。

### 方案（两层保护，答辩可讲清取舍）
1. **进程内按 `sender_id` 串行**：`asyncio.Lock` 字典，单实例内彻底消除竞态；锁获取带超时（默认 10s），超时返回 409。
2. **数据库乐观锁**：`dialogue_states` 增加 `version INT NOT NULL DEFAULT 0`；
   - 更新语句 `UPDATE ... SET state_json=?, version=version+1 WHERE sender_id=? AND version=?`；
   - 影响行数为 0 → 抛 `StateConflictError`，接口返回 409 `DIALOGUE_STATE_CONFLICT`，提示客户端重试；
   - 新建行 `version=1`。
3. **兼容迁移**：启动时检查 `information_schema.columns`，缺列则执行 `ALTER TABLE dialogue_states ADD COLUMN version INT NOT NULL DEFAULT 0`；同时提供 `sql/migrations/20261120_dialogue_state_version.sql`。
4. 失败语义：不静默重放用户消息（避免重复扣款/重复建单），只返回 409；由前端重试。

### 改动清单
- `assistant/repository/orm/dialogue_state.py` 增加 `version`；
- `assistant/repository/dialogue_repository.py` 重写 `load_state` / `save_state`，新增 `StateConflictError`；
- `assistant/utils/db.py` 增加 `ensure_schema()`；
- `assistant/service/dialogue_service.py` 引入会话锁与冲突转换；
- `assistant/api/app.py` 注册 `StateConflictError` → 409。

### 验收标准
- 单测：模拟两路读取同一版本，第二路保存抛 `StateConflictError`；
- 单测：同一 `sender_id` 并发两次 `run`，最终两条 turn 都在（锁生效）；
- 迁移脚本可在旧表上执行一次且幂等。

## 6. M4 RAG 落地（P1）

### 现状问题
`RagProvider` 只是向 `finance_rag_base_url/retrieve` 转发；不配置 URL 时检索为空，等于没有 RAG。

### 目标链路
```
知识库 Markdown → 章节切块（300 字，重叠 50）→ 向量化 → 向量库 top20
→ 重排（关键词/实体 + 可选 cross-encoder）→ top5 → 拼进 Prompt
```

### 设计（离线可跑，在线可升级）
- `assistant/rag/corpus.py`：加载 `finance-assistant/knowledge_base/*.md`，按标题与段落切块，生成稳定 `chunk_id`；
- `assistant/rag/embedding.py`：
  - `HashingEmbedder`：字符 2/3-gram 哈希到 512 维并 L2 归一化，纯 Python、确定性、无外网依赖（默认）；
  - `SentenceTransformerEmbedder`：`sentence-transformers` + `BAAI/bge-small-zh-v1.5`，装了才启用；
- `assistant/rag/store.py`：内存向量库（余弦相似度）+ JSON 持久化；检测到 `chromadb` 时自动切换；
- `assistant/rag/rerank.py`：`KeywordReranker`（bigram 重叠 + 意图词加权 + 标题命中）；检测到 `sentence-transformers` 时可切 `bge-reranker-base`；
- `assistant/rag/retriever.py`：`RagRetriever.retrieve(query, top_k=5)`，`embed → top20 → rerank → top5`；
- `assistant/rag/dataset.py`：20 题评测集（问题 + 期望 chunk 来源 + 答案关键词）；
- `assistant/rag/evaluation.py`：
  - `recall@k`：top-k 中是否命中任一期望来源；
  - `answer_hit_rate`：期望关键词在召回内容中的覆盖率（≥0.6 记为命中）；
- `assistant/rag/cli.py`：`python -m assistant.rag.cli ingest | query | eval`；
- `assistant/knowledge/provider.py`：`RagProvider` 优先本地检索，未建索引时自动构建；保留远程 URL 作为兜底。

### 验收标准
- `python -m assistant.rag.cli eval` 输出 20 题明细与汇总；
- `recall@3 ≥ 0.85`、`answer_hit_rate ≥ 0.80`（默认哈希向量 + 关键词重排）；
- 单测覆盖：切块边界（空文档/超长段落/重叠）、检索 top-k、评测指标计算；
- 文档记录真实评测数字与失败样例。

### 回滚点
`RagProvider` 开关 `RAG_ENABLED`；关闭后行为与补强前一致。

## 7. M5 SSE 流式输出（P1）

### 接口
`POST /api/chat/stream`，`Content-Type: text/event-stream`。

事件顺序（固定）：
```
event: status   data: {"stage":"accepted","request_id":"..."}
event: status   data: {"stage":"executing"}
event: message  data: {"index":0,"delta":"...","object":null}
event: message  data: {"index":0,"delta":"...","object":null}
event: status   data: {"stage":"completed","message_id":"..."}
event: done     data: {"message_id":"..."}
```
- 错误：`event: error  data: {"code":"...","message":"..."}`，随后 `done`；
- 心跳：空闲每 15s 发送 `: ping` 注释行，防止网关断连；
- 文本按 24 字符分块，块间 `await asyncio.sleep(0)` 让出事件循环；
- 文档中明确：当前引擎同步产出结果，SSE 做的是“结果分块下发 + 状态事件”，后续替换为 LLM token 回调只需改一个生成器。

### 改动清单
- `assistant/api/sse.py`（新增）：事件格式化、分块器；
- `assistant/api/chat_router.py`：新增 `stream` 路由；
- `assistant/api/app.py`：确认不启用 gzip 等会缓冲流的中间件；
- 单测：事件顺序、SSE 帧格式、异常时 error + done。

### 验收标准
- `curl -N` 能看到 status → message → done；
- 前端可选用 `fetch + ReadableStream` 消费；
- 原有 `/api/chat` 行为不变。

## 8. M6 可观测性增强（P2）

## 11. 面试答辩要点（改完之后必须能讲）

1. **为什么不用“重试 + 重新规划”解决并发？** 因为重新调用 LLM 会重复产生副作用（重复建单、重复扣款），所以选择“会话级互斥 + 版本号冲突返回 409”，让客户端幂等重试。
2. **为什么 RAG 默认用哈希向量？** 保证无外网、无 GPU 也能跑评测；接口抽象为 `Embedder`，生产替换 bge-small 只需改配置。
3. **recall@3 怎么算？** 每题标注期望来源 chunk，top-3 命中任一即算召回；答案命中率看期望关键词覆盖率。
4. **SSE 为什么不是“真 token 流”？** 当前引擎是同步产出，先把协议、状态机、异常与心跳做对；接 LLM 流式只需把生成器换成 `llm.astream`。
5. **限流为什么按主体而不是全局？** 避免单个客户刷爆影响其他人；实现是滑动窗口，单机内存版，多实例需换 Redis。
6. **审计为什么异步且失败不影响主流程？** 审计是旁路能力，不能因为审计库抖动导致业务失败；同时只存 token 摘要，避免敏感信息落库。
